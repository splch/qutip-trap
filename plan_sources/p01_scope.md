## 1. Purpose, scope and what "first principles" means here

### 1.1 Goal

Build a Python package, `qutip_trap`, that takes a quantum circuit and returns measurement results the way a trapped-ion quantum processor does, by simulating the physical process that produces those results rather than by applying ideal gate matrices with an error model bolted on. The chain the simulator reproduces is:

1. A trap potential holds N ions of a chosen species; their equilibrium positions and collective motional modes follow from the trap parameters and the Coulomb interaction.
2. Laser cooling and optical pumping prepare the motional and internal states; the result is a thermal (or near-ground) motional state per mode and a qubit state with a physical preparation error.
3. The circuit is compiled to the machine's native gates and then to a pulse schedule: for each pulse, which ions are illuminated, with what Rabi frequency envelope, frequency (detuning), phase, and duration, all taken from calibrations the simulator itself performs on the simulated device.
4. Each pulse evolves the joint state of qubits and motional modes under the spin-motion Hamiltonian, with heating, dephasing, photon scattering, addressing crosstalk and laser noise entering as physical channels with rates derived from device parameters.
5. Measurement is state-dependent fluorescence: photon counts over a detection window, with leakage between bright and dark manifolds, detector efficiency, background, and neighbour crosstalk; a threshold or time-resolved discriminator turns counts into bits.
6. Results are returned per shot (bitstrings, and optionally the raw photon-count records), aggregated into counts and probabilities, in a format compatible with what a cloud QPU returns.

### 1.2 What "exactly" can and cannot mean

The simulator is exact at the level of a well-defined physical model, and honest about the three places where any simulation of this system approximates:

- **Model level.** Each ion is a small set of electronic levels (the two qubit levels plus, where it matters, the leakage manifold), each motional mode is a quantum harmonic oscillator, and light couples to them through the Hamiltonians in Part II. The optical rotating-wave approximation (dropping terms at twice the optical frequency) is taken everywhere; its neglected terms are of relative size Ω/ω_optical, below 10⁻⁸ in every regime of interest. Nothing else is dropped by default: the carrier, every sideband, Debye-Waller factors, off-resonant terms and the full time dependence of every pulse are kept, because the Hamiltonian is built from the exact displacement operator e^{iη(a+a†)} rather than from its Lamb-Dicke expansion. Two approximations of comparable size accompany it in Raman drives, both reported with their magnitude: the adiabatic elimination of the far-detuned excited manifold, whose residual excited population is exactly what the scattering channels use, and the replacement of the counter-rotating two-photon pairing at twice the qubit splitting by its second-order frequency shift (Section 4.5.4). The Lamb-Dicke and rotating-wave-on-the-sidebands approximations are available as switchable options for speed and for reproducing textbook results, never as the default.
- **Truncation level.** Motional Fock spaces are truncated. Truncation is controlled by a convergence policy (Section 5) and every run reports the population that reached the truncation boundary, so a result is either converged or flagged.
- **Size level.** The joint spin-plus-motion state of N ions and M modes lives in a space of dimension 2^N × Π_m d_m that becomes intractable beyond a joint dimension of a few thousand, that is two or three ions with two or three dynamically resolved modes at exact fidelity, or more ions with fewer resolved modes and frozen spectators (Section 5.4, from the measured cost model of Section 11). Above that, the simulator switches to a gate-local exact mode (Section 5.4) in which each pulse is simulated exactly on the ions it addresses together with every mode they couple to, and the motional state is carried between gates by a tracked model. The plan specifies the approximation that mode introduces, how it is validated against the fully joint mode where both are feasible, and how the loss of exactness is reported to the user.

### 1.3 Non-goals for the first release

`- Shuttling and QCCD transport dynamics: the simulator models a single crystal in one zone, and transport heating enters only as a phenomenological per-transport quanta budget if a user supplies it. Run 5 nevertheless specified the physics at the equation level, because the budget has to be replaced eventually and because the objects it would consume already exist: Section 4.6 is that specification and milestone M12 (Section 10) is its work breakdown, with the interfaces Appendix E freezes chosen so that picking it up needs no change to the public surface. Nothing in the first release depends on Section 4.6, and a per-transport quanta budget remains the only transport input `run` accepts.`
- Photonic interconnects.
- Quantum error correction logic (the simulator runs circuits; a QEC stack is a client).
- Compilation optimality (the compiler must be correct and produce the native gate set; gate-count optimization beyond the standard identities is a client concern).
- Crystal melting and recrystallization dynamics: background-gas collisions are modelled as instantaneous events with an outcome distribution (heating kick, reorder permutation, ion loss or dark-ion formation; Section 6.7) and reported as heralded or discarded shots, not as molecular dynamics of the melt.
- Mixed-species dynamics in the first release: the crystal module computes mixed-species equilibrium positions, normal modes and per-species Lamb-Dicke parameters from the start (Section 4.1.7), but sympathetic cooling is modelled at the rate level only (Section 4.2.5) and no gate on a mixed crystal is scheduled or validated.

### 1.4 Users and interfaces

The primary user writes or imports a circuit, picks a device model (species, ion count, trap frequencies, beam geometry, noise parameters), and asks for results. The package exposes: a device model API; a native-gate circuit API (GPi, GPi2, MS with two phases and an angle, ZZ, virtual RZ) plus a compiler from standard gates; importers for OpenQASM 2 and for the IonQ circuit JSON format; a `run(circuit, shots)` entry point returning a results object; and a lower-level "experiment" API (Rabi scan, Ramsey, sideband spectroscopy, gate scans, heating-rate measurement) that the calibration layer uses and that users can call to reproduce laboratory measurements on the simulated device. A separate application package (Section 14), which uses only this public API, presents the same run at five zoom levels, from a cloud-style histogram down to the Hamiltonian terms being integrated, and can run the machine from any of them.

### 1.5 Constraints inherited from the environment

Python 3.13 (pinned by mise), `uv` for environment and dependency management, QuTiP 5.3.x as the simulation engine (verified installed version 5.3.1 with NumPy 2.5.2 and SciPy 1.18.1 on this machine), NumPy and SciPy as the numerical base. Cython is needed for compiled string coefficients in QuTiP; the plan uses NumPy-array and Python-function coefficients so Cython is optional. No other simulation framework is used. Plotting (matplotlib) is an optional dependency for the experiment API only. The graphical front end uses Flet (flet.dev), a Python framework that renders through Flutter: one code base gives a native desktop window, a browser UI served from the host process, or packaged desktop and mobile bundles, and it ships `flet-charts` with LineChart, ScatterChart, BarChart, MatplotlibChart and PlotlyChart controls for the experiment plots. Flet is an optional extra so the physics core has no UI dependency. Two Flet facts shape the design: event handlers may be async and the page offers `run_task` and `run_thread` for work off the UI loop, so simulations run in worker processes and post progress through the page's pubsub; and Flet's static web packaging runs Python in the browser through Pyodide, which cannot host QuTiP and is three to five times slower than native Python, so the browser mode used here is the served mode where Python stays on the host.
