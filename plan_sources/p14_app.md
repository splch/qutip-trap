## 14. The zoomable application (milestone M11)

### 14.1 The idea and the contract

The application presents one simulated trapped-ion quantum computer at five levels of abstraction. The user starts where a cloud customer stands, with a circuit and a histogram, and zooms in step by step until the screen shows the Hamiltonian terms, matrix elements and collapse operators that the simulator is actually integrating. Every level is runnable: the user can execute the machine while looking at it from any height. The application is a separate package, `qutip_trap_app`, that depends on the released `qutip_trap` and uses only its public API. Nothing in the core library is written, scheduled or changed for the GUI: milestones M0 to M10 do not depend on M11, the core's CI does not run the app's tests, and when the app needs something the core lacks, that need is filed as a core feature request and judged on the core's own merits while the app works around it on its own side. Two axes are kept separate in the design. The **abstraction of the view** is what the screen shows. The **fidelity of execution** is which engine of Section 5.4 computed it. The zoom ladder pairs a default engine with each level, but any level can display a run made by a deeper engine, and shallower engines are always labelled as derived.

Four rules make the ladder honest rather than decorative.

1. **One record, many views.** Every level is a view over the same run record (Section 14.3). Nothing on any screen comes from a separate illustrative model. A histogram bar is the count of recorded shots; a Bloch vector is the reduced state of the recorded joint state; an ion's drawn position is the equilibrium solver's output at scale.
2. **Coarse-graining commutes with simulation, within a stated bound.** Running at a shallower fidelity must reproduce the deeper engine within the bound the shallower engine reports (the residual displacement of GATE_LOCAL, the channel-derivation residual of the app-side channel replay). The app can check this on demand, and Section 9.11 tests it.
3. **Every displayed formula and number carries its provenance.** The four tags of Section 1 appear as chips on the screen, linked to the Part II item and its source. A quantity without a tag is a bug.
4. **Every result carries its convergence report.** The truncation-boundary population and the tolerance-halving check of Section 5.5 are shown with every trace, and a failing check colours the result rather than hiding it.

### 14.2 The zoom ladder

| Level | What the user sees | What the user can change | Default engine | Zoom-in targets |
|---|---|---|---|---|
| 0, Machine | The device card (species, ion count, native gate set, calibrated gate errors, SPAM), a circuit editor with OpenQASM 2 and IonQ JSON import, shot count, the results histogram with counts and probabilities, and the compiler's target distribution shown beside the simulated one and never in its place | Circuit, shots, qubit-to-ion mapping | Channel replay (app-side, built from the core's Section 6.8 channel summaries), labelled as derived | A histogram bar opens the shots behind it; a shot opens its photon-count records; a gate opens Level 1; the device card opens the Level 4 pages; the SPAM figure opens the readout page |
| 1, Circuit | The compiled native-gate timeline on ions (GPi, GPi2, MS or XX, ZZ, virtual-Z frame updates), each gate with its target unitary, calibrated parameters (χ, phases, duration) and the error channel derived for it; the register state after each gate as reduced density matrices, Bloch vectors and Pauli expectations; the phase register per ion | Gate parameters, compiler template choices, idle intervals | Channel replay or deeper | A gate opens its pulses at Level 2; a channel opens its derivation (process tomography of the simulated pulse); the phase register opens the virtual-Z rule with its pinning test (Section 7.6) |
| 2, Schedule | Pulses on a time axis: which ions each beam illuminates and from which direction, the tones with their detunings drawn against the mode spectrum beneath, phases, amplitude and frequency waveforms with their segment tables, durations and dead times, the crosstalk light on neighbours, and loop-closure indicators per mode | Waveforms, detunings, amplitudes, durations, crosstalk parameters | GATE_LOCAL | A pulse opens Level 3; a tone opens the Hamiltonian term it produces; a mode opens the crystal page at Level 4 |
| 3, Dynamics | Inside one pulse for one dynamical sample: qubit populations and coherences against time, Fock distributions per mode as heatmaps, the spin-dependent phase-space trajectories α_m(t) closing or failing to close, the accumulated entangling angle χ(t), the Debye-Waller factor, quantum jumps (heating, scattering) marked where they occurred, the process matrix of the finished pulse, and the quasi-static noise values drawn for this sample | Initial motional state per mode, noise rates, truncation caps and solver tolerances (with the convergence check re-run) | JOINT_EXACT, re-simulated on demand for the zoomed pulse | A Hamiltonian term opens its matrix elements and the Ω_{n′,n} table at Level 4; a jump opens the collapse operator and the derivation of its rate |
| 4, Physics | The first-principles pages: species (level diagram with the driven transitions, branching ratios, hyperfine structure, the qubit pair), trap (electrode potentials to Mathieu a and q to β and ν, pseudopotential, the stability diagram with the operating point, micromotion), crystal (equilibrium positions to scale, normal modes with animated eigenvectors, η per ion, mode and Δk), light (beams as fields with k-vectors and polarizations, the Raman configuration, Ω from intensity, Stark shifts, scattering rates against detuning), noise (the S_E model and heating rates, dephasing spectra, the crosstalk matrix), cooling (stages and n̄(t) per mode from the rate or master equations), readout (R_∘, R_d and R_b against saturation, count histograms, the discriminator and its threshold, the error budget), and the Hamiltonian builder page showing the H(t) terms and collapse operators assembled for a chosen pulse | Any device parameter: voltages and rf amplitude, laser powers, detunings and geometry, temperatures, noise densities, detection window | JOINT_EXACT with the preparation and readout layers, so a run is the whole process from cooling to photon records | Zooming out re-derives every level above through the calibration emulation |

A **numerics panel** accompanies every level: Hilbert-space dimensions and truncation caps in use, boundary population, the tolerance-halving result, trajectory count, wall time, and the engine that produced what is on screen.

### 14.3 One run record, many views

The run record is the single data structure the levels read. Job (device-model hash, seed, package version, convergence policy) → compiled circuit → schedule → per-sample dynamics traces → readout records → results. A dynamics trace stores, at configurable sample times, expectation values, reduced internal-state density matrices, per-mode occupation distributions, the α_m(t) trajectories and the jump list; full joint kets are stored only while the joint dimension is below a configurable cap. Anything not stored is recomputed on demand: zooming into a pulse re-simulates that pulse alone from its recorded initial state and its recorded noise sample, which by the measured timings of Section 11.1 takes about half a second for a 100 µs entangling pulse at joint dimension 48, two seconds at 256 and minutes at 2048; the record therefore stores the traces of the run itself, re-simulation is immediate only for small joint spaces, larger ones are filled in by a background job, and every result is cached in the record. Readout records hold photon counts per ion per sub-bin and the discriminator's posterior, so a shot can be opened down to its count trace. Records export to a JSON document with binary arrays (HDF5 optional) and re-import bitwise, which is what makes a published screenshot reproducible.

### 14.4 Knobs propagate downward

The device model at Level 4 is the single source of truth. A change there, a trap voltage, a beam power, a detection window, re-derives the analytic layer immediately (mode structure, η, pulse-solver solutions, the closed-form estimates of the gate channels, the device card's estimated columns) and invalidates the calibration table, whose regeneration by simulated experiment (Section 7.5) takes hours at the measured rates of Section 11.1 and runs only as a user-initiated background job; dependent views show a stale badge until that job completes, and the device card states which of its numbers are analytic estimates and which are calibrated. A change at a shallower level is a request rather than an edit: asking for XX(0.3) at Level 1 invokes the pulse solver; setting a detuning by hand at Level 2 is applied as written, and the gate at Level 1 then displays its actual unitary, not the requested one. Requests the device cannot satisfy are shown with the reason, for example loop closure impossible within the power limit or a requested angle outside the calibrated range. At no point does the app let a level float free of the device model.

### 14.5 Correctness affordances

- **Provenance chips** on every formula and number, generated from a provenance ledger: a YAML file kept beside the plan with one record per quantity (`id`, `symbol`, `tag`, `section`, `source`, `equation`, `corrected_form`), which the core's `Device.derived()` provenance and the app's chips both consume, so the Section 9.11 static test is a set difference over ids rather than a hand-maintained index; hovering a chip shows the tag, the source and the corrected form where the plan corrects the source.
- **Convergence badges** on every result and trace, red when the halving test of Section 5.5 fails.
- **Verify deeper.** At Levels 0 to 2 one action runs the same job at the next-deeper engine, on a subset of shots when the full run would be slow, and shows the discrepancy against the bound of Section 9.8 or the channel-derivation residual.
- **Target beside simulated.** Levels 0 and 1 show the compiler's target semantics next to the simulated result, never as the result.
- **Units and conventions.** Frequencies are displayed in Hz with the 2π conversion visible; the convention row of Section 13 that governs a displayed quantity is one hover away.
- **No cartoons.** Every drawn element is computed: ion positions from the equilibrium solver, beams from the configured geometry, mode vectors from the Hessian, spectra from the built Hamiltonian. The few illustrative elements, such as a level diagram's vertical spacing, are labelled "not to scale".
- **Reproducibility.** Seed, device hash, package version and convergence report travel with every exported record.
- **Presets from the validation suite.** Any entry of Section 9 can be loaded as a device configuration plus experiment, for example Harty's microwave randomized benchmarking, Kirchmair's thermal Mølmer-Sørensen scan or Myerson's readout optimum; the app runs it and places the published number beside the simulated one with the provenance chip.
- **Explain panel.** At every level, the Part II subsection that governs what is on screen is shown beside it.

### 14.6 Flet implementation

- **Routes mirror the ladder** with the declarative `ft.Router` of Flet 0.85: `/job/{id}` for Level 0, `/job/{id}/circuit/{gate}` for Level 1, `/job/{id}/schedule/{pulse}` for Level 2, `/job/{id}/dynamics/{pulse}/{sample}` for Level 3, and `/device/{page}` for the Level 4 pages, with a breadcrumb zoom bar and keyboard zoom in and out. Browser history works in the served web mode because routes are real.
- **Core contract.** The app calls only public core API that exists for the core's own reasons: the device model and its hash, the `Machine` (the device with its roles, its calibration table and its policy) with `run(circuit, shots)` and `submit(circuit, shots)` (a `Job` whose `RunSpec` is the record of the request; 0.4.0) and the `Result` with its diagnostics and convergence report, the experiment API on the machine, the per-pulse evolution and process-tomography entry points that the core's validation suite and Section 6.8 reporting already use (with the traces' per-time Fock marginals and the GATE_LOCAL walk's per-step register since 0.4.0), and the compiler's target unitaries. The app imports only the documented rung modules (`qutip_trap`, `qutip_trap.circuit`, `.schedule`, `.dynamics`, `.physics`, the laboratory and `qutip_trap.api`), so its `CORE_GAPS` list is empty from 0.4.0 on. The channel-replay engine (`replay.py`) is built app-side from the Section 6.8 summaries. If a zoom view needs data the core does not expose, the app records the gap and shows the view as unavailable rather than patching the core.
- **Layering.** `viewmodel/` is pure Python with no Flet import: it turns run records into view data, performs the coarse-graining, and resolves provenance; it is where the correctness tests run. `views/` holds the Flet controls per level. `workers.py` runs core calls in a `ProcessPoolExecutor`, streaming progress and partial results through `page.pubsub`; view updates are scheduled with `page.run_task`, so the UI never blocks on a solver.
- **Charts.** `flet-charts` LineChart and ScatterChart for time series, calibration scans and phase-space loops; BarChart for histograms; MatplotlibChart for level diagrams, mode eigenvectors and the stability diagram; `ft.RawImage` (Flet 0.86) for streamed heatmaps such as Fock distributions and Wigner functions; DataTable for matrix elements, segment tables and parameter tables.
- **Testing.** pytest on the view-models (coarse-graining identities, provenance coverage, record round trips); `flet test` integration tests for navigation and run flows; the physics itself is never tested through the UI.
- **Packaging.** `flet run` for the desktop window during development, `flet run --web` for the served browser mode, `flet build macos`, `windows` or `linux` for distributable bundles with the physics dependencies installed as binary wheels. The static Pyodide web build is not a target (Section 1.5).

### 14.7 Interactive budgets

|---|---|---|

### 14.8 Out of scope for M11

Live hardware submission, multi-user server deployment, and mobile bundles (possible with `flet build`, but wheel availability of the physics stack on Android and iOS is not part of this plan).
